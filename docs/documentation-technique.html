Présentation

DataShare permet d'envoyer un fichier (1 Go maximum), de choisir sa durée de conservation (de 1 à 7 jours) et un mot de passe facultatif, puis d'obtenir un lien de partage. Toute personne qui possède le lien peut consulter la page de téléchargement, saisir le mot de passe si besoin et télécharger le fichier, sans compte. Un utilisateur avec compte retrouve ses envois dans « Mon espace », où il voit leur état (actif, expiré) et peut les supprimer. Passé la date d'expiration, le lien répond « expiré » et le contenu est supprimé du disque.

1. Architecture de l'application

L'application se compose de trois zones : une application web monopage (Vue) qui s'exécute dans le navigateur, une API REST (Symfony) qui porte toute la logique, et des données réparties entre PostgreSQL (comptes, informations sur les fichiers) et le disque du serveur (contenu des fichiers). Le navigateur n'accède jamais directement à la base ni au disque : tout passe par l'API.

Déroulement d'un partage

  1. Le navigateur envoie le fichier en multipart/form-data à POST /api/files. Le serveur vérifie la taille (1 Go), la durée (1 à 7 jours) et hache le mot de passe éventuel.
  2. Le contenu est écrit sur le disque sous un nom aléatoire ; une ligne est créée en base avec un lien (token de 8 caractères). La réponse contient l'adresse de partage <FRONT_URL>/<token>.
  3. Le destinataire ouvre le lien : la page appelle GET /api/shared/{token} pour afficher le nom, la taille et l'expiration.
  4. Pour un fichier protégé, le mot de passe est envoyé à POST /api/shared/{token}/unlock ; le serveur répond par une adresse de téléchargement contenant un ticket signé valable 10 minutes.
  5. Le navigateur ouvre GET /api/shared/{token}/download : le fichier est envoyé en flux, en pièce jointe.
  6. Chaque heure, la tâche de purge supprime du disque le contenu des fichiers expirés.

ChampRègle
user.emailEnregistré en minuscules : Bob@x.com et bob@x.com désignent le même compte. Unique.
user.passwordHash (algorithme « auto » de Symfony). Jamais renvoyé par l'API.
shared_file.owner_idVide pour un envoi anonyme. Clé étrangère avec ON DELETE SET NULL : supprimer un compte ne supprime pas les lignes.
shared_file.stored_nameNom aléatoire (32 caractères hexadécimaux) du fichier sur le disque. Devient vide quand le contenu est purgé : l'utilisateur voit alors « Expiré ».
shared_file.tokenPartie aléatoire du lien : 8 caractères parmi 62, soit environ 218 000 milliards de combinaisons (random_int). Unique.
shared_file.password_hashVide si le fichier n'est pas protégé. Sert aussi de clé de signature du ticket de téléchargement.
shared_file.sizeEntier de 32 bits : suffisant, la limite est de 1 Go.
expires_atDate de création + 1 à 7 jours. Vérifiée à chaque appel de l'API, indépendamment de la purge.

Cycle de vie d'une ligne shared_file : créée à l'envoi → expirée à expires_at (l'API répond 410) → purgée (contenu supprimé, stored_name vide ; la ligne est conservée pour un propriétaire, supprimée pour un envoi anonyme) → supprimée si le propriétaire la supprime.

4. Documentation de l'API

L'API est décrite au format OpenAPI 3, générée depuis le code (attributs #[OA\…] sur les contrôleurs et le DTO). Elle est consultable :

  • en ligne, quand le backend tourne : http://127.0.0.1:8000/docs/ (interface Swagger, en français, utilisable hors ligne) ;
  • en JSON : /api/doc.json ; en fichier : docs/openapi.yaml (importable dans Postman ou Insomnia) ;
  • à regénérer après un changement de l'API : cd backend && composer docs.

Pour essayer les routes protégées dans Swagger : POST /api/register, puis POST /api/login, copier le token reçu et cliquer sur « Authorize ».

MéthodeRouteAccèsRôle et réponses principales
POST/api/registerpublicCrée un compte (email, mot de passe de 8 caractères minimum). 201 ; 409 email déjà utilisé ; 422 erreurs de validation.
POST/api/loginpublicRenvoie un jeton JWT valable 1 heure. 401 identifiants invalides ; blocage après 5 échecs en 15 minutes.
GET/api/mejetonUtilisateur connecté (id, email, rôles). 401 sans jeton valide.
POST/api/filespublicEnvoie un fichier (file, expiration 1 à 7, password facultatif). Le fichier est rattaché au compte si un jeton valide est fourni. 201 avec le lien ; 422 ; 429 au-delà de 10 envois par heure pour un visiteur.
GET/api/filesjetonListe de mes fichiers, du plus récent au plus ancien, y compris les expirés.
DELETE/api/files/{id}jeton, propriétaireSupprime la ligne et le contenu. 204 ; 404 si le fichier n'existe pas ou appartient à quelqu'un d'autre.
GET/api/shared/{token}publicNom, taille, type, protected, expiresAt. 404 lien inconnu ; 410 expiré.
POST/api/shared/{token}/unlockpublicVérifie le mot de passe, renvoie l'adresse de téléchargement (avec ticket pour un fichier protégé). 403 mot de passe incorrect ; 422 manquant ; 429 trop d'essais.
GET/api/shared/{token}/downloadpublic (ticket)Envoie le fichier en flux, en pièce jointe, avec reprise possible (Range). 403 ticket absent ou invalide ; 410 expiré.
GET/api/healthpublicÉtat du service.

Format des erreurs

Toutes les erreurs sont en JSON. Les erreurs de validation sont rattachées à un champ, ce qui permet à l'interface de les afficher sous le bon champ :

{ "message": "Cette adresse email est déjà utilisée.",
  "violations": [ { "propertyPath": "email", "title": "Cette adresse email est déjà utilisée." } ] }

Codes utilisés : 200/201/204 succès, 401 non connecté, 403 mot de passe ou ticket invalide, 404 inconnu, 409 doublon, 410 expiré, 422 validation, 429 trop d'essais.

Des tests (ApiDocumentationTest) échouent si une route n'est pas documentée, si un cadenas ne correspond pas à la sécurité réelle, si une référence est cassée ou si docs/openapi.yaml est périmé.

5. Sécurité et gestion des accès

Le détail complet (avec la liste des tests qui prouvent chaque point) est dans SECURITY.md. En résumé :

Authentification et accès

SujetMesure
ComptesMot de passe haché (jamais stocké ni renvoyé en clair). Connexion par jeton JWT signé en RS256, valable 1 heure ; un jeton falsifié, absent ou périmé est refusé (401). Même message pour « email inconnu » et « mauvais mot de passe ».
Contrôle d'accèsRoutes publiques : inscription, connexion, santé, documentation, liens de partage, envoi. Tout le reste exige un jeton. Un utilisateur ne voit et ne supprime que ses fichiers (404 pour ceux des autres, sans révéler leur existence).
Fichiers protégésMot de passe haché. Après vérification, un ticket signé (HMAC-SHA256, 10 minutes, propre au fichier et non falsifiable, comparé en temps constant) autorise le téléchargement. L'expiration est vérifiée à chaque appel, même avec un ticket valide.

Protection contre les abus

AbusMesure
Force brute sur un fichier5 essais de mot de passe par 15 minutes, par lien et par adresse IP, puis 429 avec Retry-After ; même le bon mot de passe est refusé pendant le blocage.
Force brute sur la connexion5 échecs par 15 minutes, par email et adresse IP.
Remplissage du disque1 Go maximum par fichier ; 10 envois par heure et par IP pour un visiteur non connecté.
Deviner un lien8 caractères aléatoires (environ 218 000 milliards de combinaisons).

Protection des données et du navigateur

RisqueMesure
Injection SQLToutes les requêtes passent par Doctrine, avec des paramètres liés.
XSSVue échappe toutes les valeurs affichées ; aucun v-html dans le code. Les fichiers sont toujours envoyés en pièce jointe (Content-Disposition: attachment) avec X-Content-Type-Options: nosniff : le navigateur ne les interprète jamais.
CSRFLe jeton est envoyé dans un en-tête par le code de l'application, pas dans un cookie : le navigateur ne l'ajoute jamais de lui-même.
Chemins de fichiersStockage hors du dossier public, nom aléatoire ; le nom d'origine n'est qu'en base et est nettoyé (../x.jpg devient x.jpg).
Fuite d'informationLes réponses publiques ne contiennent ni propriétaire, ni nom sur le disque, ni hash.
SecretsAucun secret dans git : .env.local et les clés JWT sont ignorés ; APP_SECRET et la phrase secrète sont générés au hasard par les scripts d'installation.

Limites connues

Une revue de code a trouvé et fait corriger 4 problèmes importants (limitation de la connexion, quota des envois anonymes, jeton expiré à l'envoi, emails sensibles à la casse). Restent à traiter avant une vraie mise en production : HTTPS et en-têtes de sécurité (CSP) à configurer sur le serveur web, quotas par compte et plafond d'espace disque, jeton conservé dans le localStorage (cookie HttpOnly et jeton de renouvellement en piste), trusted_proxies derrière un proxy, pas de vérification des emails, fichiers non chiffrés ni analysés par un antivirus. La liste complète (13 points) figure dans SECURITY.md.

Installation automatique (recommandée)

Le script vérifie les prérequis, installe les dépendances, crée la configuration locale, génère les clés JWT, crée les bases (développement et test) et applique les migrations. Il est rejouable.

# Windows (PowerShell)
.\scripts\install.ps1 -DbUser postgres -DbPassword 'mon-mot-de-passe'

# Linux / macOS
DB_USER=postgres DB_PASSWORD='mon-mot-de-passe' ./scripts/install.sh

Options : -DbHost, -DbPort, -DbName, -FrontUrl, -Force (régénère la configuration et les clés), -SkipFrontend, -RunTests (variantes DB_HOST… et --force… pour le script Linux/macOS). Si l'utilisateur PostgreSQL n'existe pas : psql -U postgres -v db_user=datashare -v db_password='…' -v db_name=datashare -f scripts/db/init.sql.

Lancement

# terminal 1 : API
cd backend && symfony serve --no-tls -d     # ou : php -S 127.0.0.1:8000 -t public

# terminal 2 : interface
cd frontend && npm run dev                   # http://localhost:5173

L'interface appelle l'API sur /api, redirigé par Vite vers http://127.0.0.1:8000. La documentation Swagger est sur http://127.0.0.1:8000/docs/. La purge se planifie séparément : cd backend && php bin/console app:files:purge-expired (toutes les heures).

Toute la configuration locale est dans backend/.env.local (ignoré par git) ; le fichier backend/.env n'est jamais modifié.

8. Utilisation de l'IA dans le développement

DataShare a été développé avec l'assistant de programmation Claude Code (modèles Claude d'Anthropic). L'IA a écrit une grande partie du code, des tests et de la documentation ; le développeur a cadré chaque étape, relu, exécuté et validé, et pris les décisions de conception. Le détail est dans AI.md.

TâcheAuteur
Sujet, fonctionnalités, choix (JWT, suppression de Twig, durées, 1 Go), maquettes Figmadéveloppeur
Code de l'API, des pages, des composants, des scriptsIA, relu et exécuté par le développeur
Tests, documentation, mesures de performanceIA, à partir du code et de mesures réelles
Commitsdéveloppeur (message proposé par l'IA ; type feat(ai) pour le code essentiellement généré)

Méthode

  • Une étape à la fois : pour les sujets structurants, l'IA proposait d'abord un plan, sans toucher au code, jusqu'à l'accord du développeur.
  • Code commenté en français, avec des explications du frontend Vue par comparaison avec Symfony (store ≈ service, routeur ≈ routes.yaml + security.yaml).
  • Exécution systématique : chaque modification est suivie des tests et d'une vérification sur l'application qui tourne.

Contrôles du travail de l'IA

  • 449 tests automatisés (198 PHPUnit, 251 Vitest), dont des tests qui échouent si la documentation s'écarte du code.
  • Installation rejouée sur une copie vierge du dépôt ; scan des dépendances (composer audit, npm audit).
  • Revue de code indépendante : 8 constats dont 4 importants, tous corrigés ou documentés (limitation de la connexion, quota des envois anonymes, jeton expiré à l'envoi, emails sensibles à la casse). Un code généré se vérifie : ces défauts existaient bel et bien.

Limites et risques assumés

  • Fiabilité : l'IA peut produire du code qui semble juste et ne l'est pas ; les tests, l'exécution réelle et la revue sont les garde-fous. Elle ne remplace pas la relecture humaine.
  • Sécurité : pas de test d'intrusion indépendant ; limites connues listées dans SECURITY.md.
  • Confidentialité : les échanges transitent par le service d'Anthropic ; aucun secret réel n'est dans git (.env.local ignoré), les fichiers de test étaient fictifs.
  • Compréhension : un code non écrit par soi se comprend moins bien, d'où les commentaires et la documentation du dépôt.
  • Le projet ne dépend d'aucun outil d'IA pour fonctionner ou être maintenu : tout est dans le dépôt.
